Wichtiger Befund 2026-09-13: React-Native-`View`/`Pressable` sind implizit
`display: flex; flexDirection: column`; ein reines DOM-`div`/`button` ist
`display: block`. Mehrere frühe Umstellungen dieser Session haben
`alignItems`/`justifyContent`/`gap`/`flexDirection` übernommen, ohne das
fehlende `display: flex` zu ergänzen, wodurch die Ausrichtung/der Abstand
im echten Browser wirkungslos gewesen wäre (von den Unit-Tests nicht erkannt,
da sie nur das Style-Objekt prüfen, nicht das gerenderte Layout). Behoben in
`appStyle.containerCenter*`/`containerForInput*` (dort ist `display: flex`
für React Native ein No-op, also risikofrei für verbleibende native
Konsumenten) sowie in allen betroffenen `buttons/`- und `cards/`-Dateien
dieser Session. **Regel für alle künftigen `View`→`div`-Umstellungen:** jedes
neue `div`/`button` braucht explizit `display: "flex"` (plus `flexDirection:
"column"`, sofern keine `"row"` beabsichtigt ist), sooft `alignItems`,
`justifyContent`, `gap`, `flexWrap` oder `flexDirection` im selben
Style-Objekt vorkommen oder eine Eltern-Kind-`flex: 1`-Streckung erwartet
wird.

Zweiter Befund (gleiche Ursache, gleiche Session): React Native/Yoga
behandelt jede `View` implizit als `position: relative`; im DOM ist der
Default `position: static`. Ein `position: "absolute"`-Kind fand seinen
CSS-Containing-Block dadurch unter RN immer beim direkten Eltern-Element,
im DOM aber erst beim nächsten explizit positionierten Vorfahren (im
schlimmsten Fall dem Body). Ein Fall davon wurde in `WnaButtonHeader`
gefunden und behoben (`styles.inner` bekam `position: "relative"`), bevor er
sichtbar geworden wäre. **Zusätzliche Regel:** sooft ein umgestelltes
`div`/`button` ein `position: "absolute"`-Kind enthält (direkt oder über
verschachtelte reine Layout-`div`s), muss der unmittelbare Eltern-Container
explizit `position: "relative"` bekommen, sofern er nicht ohnehin schon
`position: "absolute"`/`"fixed"`/`"sticky"` trägt.

Aktueller Fokus: Phase 2 mit verbleibenden Native-UI-Primitives abschließen,
danach den Drawer in Phase 3 durch Web-Navigation ersetzen. Erst dann können
die transitiven Router-/Drawer-Dependencies entfernt werden.
Neue Phasen werden erst begonnen, wenn die jeweils aktiven Exit-Kriterien erfüllt
sind.

## Ziel

Die Anwendung wird als statische, installierbare Web-PWA betrieben. Native
Rendering- und Navigationsabstraktionen werden entfernt. Verhalten, Inhalte,
Barrierefreiheit, Background-Image, Navigationstransitions und SEO-Policy
bleiben erhalten. Die bestehende `noindex`-Policy ist beabsichtigt und darf
nicht aktiviert werden.

## Leitplanken

- Web-Plattform und Browser-APIs sind die primäre Laufzeit.
- Semantisches HTML und CSS ersetzen React-Native-Layout-Primitives.
- CSS-Transitions oder Web Animations ersetzen Reanimated.
- `srcset`/`picture` ersetzen die plattformübergreifende Bildauflösung.
- `expo-constants`, `expo-linking`, `react-native-gesture-handler`,
  `react-native-reanimated`, `react-native-safe-area-context` und
  `react-native-screens` sowie der Reanimated-Peer `react-native-worklets`
  bleiben bis zur Expo-Router-/Drawer-Ablösung als direkte Peer-Dependencies
  installiert; der eigene Code nutzt, wo möglich, bereits Browser-Adapter.
- Routing wird erst nach Stabilisierung der Web-Shell ausgetauscht.
- Jede Phase benötigt fokussierte Unit-, Integrations- und E2E-Regressionstests.
- Nach jeder Phase werden Lighthouse, Bundle-Größe, Accessibility und
  Navigationstransitions erneut gemessen.
