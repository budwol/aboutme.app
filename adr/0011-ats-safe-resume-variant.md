# 11. A separate, single-column resume variant is generated for ATS pipelines

Date: 2026-09-09

## Status

Accepted

## Context

The designed resume (ADR 0010) is a two-column layout: a colored sidebar carries the photo, contact details, and skill bars, while the main column carries the narrative content. Two-column layouts are a well-known weak point for Applicant Tracking Systems (ATS) — the automated software many companies use to pre-screen PDF resumes before a human sees them. Many of these systems extract text by position on the page rather than by document structure, which can interleave sidebar content into the middle of job descriptions, or drop it entirely, especially when levels of proficiency are only expressed visually (a bar's fill ratio) rather than as extractable text. Since this resume is explicitly meant to be forwarded through an HR pipeline (ADR 0010's whole premise), that risk is directly relevant, not theoretical.

## Decision

`scripts/generate-resume-pdf.cjs` now also generates `public/Portfolio-DE-ATS.pdf` and `public/Portfolio-EN-ATS.pdf` via a second render function, `writeAtsResumePdf`, called alongside the designed one in `generateResumePdf`. It deliberately gives up everything ADR 0010 added for visual polish, in favor of being unambiguous to a parser:

- Single column, full document width, top-to-bottom reading order — no sidebar, no absolute positioning.
- No photo.
- Proficiency shown as text (`"C# [Senior]"`) instead of a bar — `buildAtsSkillList`/`buildAtsSoftSkillList` produce `{ name, level }` pairs from the same `skillLevels` lookup and `softSkills` data ADR 0010 introduced, just rendered as a comma-separated line under each section instead of `drawSkillBarSection`'s bars. Tech-Stack and Tools show every item (primary and secondary together) rather than the designed version's curated, space-limited subset, since there's no sidebar height to protect here.
- Plain `Helvetica`, plain black text, standard section headings ("Kontakt", "Profil", "Tech-Stack", "Tools", "Soft Skills", "Berufserfahrung") reused from the same `LABELS` object as the designed PDF.
- Bullets are a literal `"- "` prefix with no hanging-indent treatment — visual alignment doesn't matter for a document whose only job is to be text-extracted cleanly.

It reuses `pickString`/`pickStringArray`/`formatPhoneNumber` from the designed-PDF code path (same source data, same language-fallback rules), but contact rows go through a dedicated `buildAtsContactLines` rather than `buildContactLines`: the sidebar's version shows short labels next to a recognizable icon ("LinkedIn", "Xing", a stripped-protocol "wb.wna24.de") with the actual URL living only in the link annotation — fine when a human sees the logo, invisible to a parser that only extracts visible text. `buildAtsContactLines` always prints the full address (`https://www.linkedin.com/in/...`, the complete site URL) as the visible text itself, keeping the same link annotation underneath only as an added convenience for a human who opens this exact file, never as the sole carrier of information. It gets the same "Page X of Y" footer treatment as the designed PDF (`bufferPages` + `switchToPage`), including the same margins-hazard fix from ADR 0010.

The designed PDF links to its own language's ATS counterpart from its footer ("Text-Version (ATS)" / "Text-only version (ATS)"), built as an absolute URL from `app-data.json`'s `siteUrl` (`buildAbsoluteUrl`) so the link resolves correctly regardless of where the PDF is opened from — a relative path would only resolve if the PDF happened to still be viewed from the site's own origin.

## Consequences

- Two more files to keep in sync are, in fact, _not_ a maintenance burden: both variants read the exact same `app-data.json`/`skillLevels`/`softSkills` data through the same helper functions, so there's no second copy of content to drift.
- The ATS variant is meaningfully smaller (~10KB vs. ~130KB) since it embeds no image and draws no vector graphics — worth noting if anyone goes looking for why the two files differ so much in size and assumes something is missing.
- This doesn't guarantee good ATS parsing — no PDF generator can, since every ATS product parses differently and none of them are testable from here. It removes the specific, well-documented failure modes (multi-column reading order, information conveyed only through a visual bar) that are common to point at when a resume didn't survive automated screening.
- Like the designed PDF, both ATS files are build artifacts — `.gitignore`d, regenerated by `npm run web` / `npm run export:web` / `npm run generate:resume-pdf`, not committed.
