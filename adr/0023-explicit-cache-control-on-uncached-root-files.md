# 23. Root files not covered by the hashed-asset rule get an explicit Cache-Control

Date: 2026-09-20

## Context

`nginx/site.conf` (generated by `scripts/init-process.cjs`) sets an explicit `Cache-Control` for `index.html` and `sw.js` (`no-cache`) and for hashed/versioned static assets (`public, max-age=31536000, immutable`), but `app-data.json`, `robots.txt`, `sitemap.xml`, and `llms.txt` matched none of those location blocks. They fell through to the bare `location /` block, so nginx sent no `Cache-Control` header at all for them -- flagged by an external security scan ("re-examine Cache-Control directives") and also just an unintentional gap, since none of these files are cache-busted the way images/PDFs are (see [[0006-cache-busted-static-assets]]).

## Decision

- `app-data.json` gets its own exact-match location with `Cache-Control: no-store`, matching the intent already expressed at the fetch call site (`src/app-data/index.ts` fetches it with `cache: "no-store"`).
- `robots.txt`, `sitemap.xml`, and `llms.txt` get a regex location (`\.(txt|xml)$`) with `Cache-Control: no-cache`, since they're fetched at fixed paths by crawlers/tools and aren't cache-busted.
- The resume PDFs are versioned via `getVersionedLocalAssetUrl` the same way images are (see [[0006-cache-busted-static-assets]] and ADR 0010), so `pdf` was added to the existing long-lived immutable asset rule instead of getting a separate short-cache rule.

## Consequences

- `nginx/site.conf` is generated (gitignored) -- change `scripts/init-process.cjs` and run `npm run init` to regenerate it, don't hand-edit the generated file.
- Every static file nginx serves now gets an explicit, intentional `Cache-Control` value instead of relying on nginx's undocumented default for anything that doesn't match a location block.
