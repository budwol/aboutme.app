# 5. Components follow a `WnaXxx` directory-with-barrel convention

Date: 2026-09-09

## Status

Accepted (reconstructed from existing implementation)

## Context

The component tree under `src/components/` and `src/navigation/components/` is large and needs a predictable shape so any component can be found, imported, and tested the same way.

## Decision

Every non-trivial component is named `WnaXxx`. It lives in its own directory (`WnaXxx/WnaXxx.tsx` + `WnaXxx/WnaXxx.test.tsx` + `WnaXxx/index.ts` re-exporting the default) **only if it owns at least one file beyond itself and its test** — a `wnaXxxTypes.ts`/`wnaXxxStyles.ts` side-file (ADR 14) or a private single-consumer subcomponent (below). Everything else is a single flat file directly under its category folder (e.g. `src/components/text/WnaSectionTitle.tsx`), even a large one — line count is not the criterion. This is a checkable rule (does this component's directory need to hold more than `WnaXxx.tsx`/`WnaXxx.test.tsx`/`index.ts`?), not a judgment call, precisely so it doesn't drift the way the pre-2026-09-11 wording did (see below). Categories are organized by role, not by feature: `buttons/`, `cards/`, `chrome/`, `screens/`, `sections/`, `display/`, `images/`, `effects/`, `feedback/`, `icon/`, `text/`, `theme/`.

A component's private, single-consumer subcomponent lives inside its parent's own directory (e.g. `WnaExperienceSection/WnaExperienceTimelineItem.tsx`, `WnaButtonIcon/WnaButtonIconBadge.tsx`), never flat at category level, so a reader can tell from placement alone whether a component is reusable within the category or an implementation detail of one specific component.

## Consequences

- Import paths are always `@components/<category>/WnaXxx` (or `@/navigation/components/WnaXxx`), resolved via the `@components`/`@` path aliases in `tsconfig.json`/`jest.config.cjs`, never relative deep imports.
- A reviewer can predict where a new component belongs from its role alone, and predict that `WnaXxx.test.tsx` sits next to it.
- No violations of the naming/placement convention were found during the 2026-09-09 audit.
- 2026-09-11 follow-up: a senior-level review found and fixed several drifts — `WnaDrawerMenu` had ended up under the `src/app/` route tree instead of `src/navigation/components/`; header/footer chrome components (`WnaHeader`, `WnaFooter`, `WnaContactFooter`, `WnaMultilineHeader`) had no category of their own and had been dropped into `screens/`, which is now reserved for actual routes/screen shells; and `WnaButtonIconBadge` (renamed from `WnaButtonIconInnerIcon` in a later naming pass), a private subcomponent of `WnaButtonIcon`, sat flat at category level instead of inside `WnaButtonIcon/`. See also [ADR 14](0014-wna-side-file-naming-convention.md) for the related types/styles side-file convention.
- 2026-09-11 follow-up (locality pass): the original "own directory when it has its own concerns (props, tests)" wording was vague enough that it stopped predicting reality — every component has props and tests, so it gave no actual answer. Measured against line count, the split looked arbitrary (`WnaIcon.tsx`, 23 lines, foldered; `WnaToastHost.tsx`, 164 lines, flat; a 91-line `WnaNavigationList.tsx` flat next to a 138-line `WnaNavigationItem/` foldered). The rule above replaces it with a checkable one (own directory iff it owns a side-file or private subcomponent), and ~30 components that had no such extra file were flattened back to their category root to match: `WnaNavigationItem`, `WnaStackScreenOptions`, `WnaDrawerMenu`, `WnaTabLayout`, `WnaMenuToggleButton`, `WnaHeaderRouteButton` in `navigation/components/`; `WnaContactRoute`, `WnaMenuRoute`, `WnaHomeRoute`, `WnaProjectsRoute`, `WnaBaseScreen`, `WnaWebBaseScreen`, `WnaScrollViewScreen`, `WnaLegalDocumentScreen` in `screens/`; `WnaHeader`, `WnaMultilineHeader`, `WnaContactFooter` in `chrome/`; `WnaImage`, `WnaHeroImage` in `images/`; `WnaButtonHeader`, `WnaButtonTextContent`, `WnaButtonIconText` in `buttons/`; `WnaCardVerticalSmall`, `WnaCardVerticalImage` in `cards/`; and `WnaProfileSection`, `WnaContactSection`, `WnaTechStackSection`, `WnaProjectsSection`, `WnaProfileHero`, `WnaFooterActionLink` in `sections/` (the first four renamed from `*Card` in the same pass — see [ADR 17](0017-naming-avoids-c-java-conventions.md)). `WnaProjectDetailsRoute`, `WnaExperienceSection`, `WnaButtonIcon`, `WnaBasePressable`, and `WnaImageElement` stayed foldered because they genuinely own extra files. Every move was import-path-neutral — `@components/<category>/WnaXxx` resolves identically whether `WnaXxx` is a file or a directory with an `index.ts`, so no consumer or test needed a path change, only the moved files themselves.
- 2026-09-11 follow-up (re-audit, same day): re-checking every foldered component against the rule above (not just the ones already suspected) turned up one the first pass missed — `WnaApp/` held only `WnaApp.tsx`/`WnaApp.test.tsx`/`index.ts`, kept foldered on an unwritten "it's the one root shell, it's special" exception rather than the actual rule. Flattened to `src/components/WnaApp.tsx`, same as everything else without a justifying extra file; no exception carved out for it in the rule itself. Separately, `src/constants/themePalettes.ts` (computed light/dark color palettes — real runtime data, not configuration) was moved into `src/constants/theme/` alongside its three siblings (`colors.ts`, `staticColors.ts`, `fontFamilies.ts`) it had always belonged next to; this one **did** need consumer updates (`@constants/themePalettes` → `@constants/theme/themePalettes`, 3 files) since it's outside the always-index-resolved component convention this ADR covers.
