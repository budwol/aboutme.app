# 10. A condensed resume PDF is generated at build time from the same source data

Date: 2026-09-09

## Status

Accepted

## Context

HR departments circulate candidate documents as PDF files. The portfolio site's `app-data.json` already holds the profile, work experience, tech stack, and contact details needed for a classic CV, but also holds private side-project details that don't belong in a document meant to be forwarded around a company. Maintaining a second, hand-written CV document alongside `app-data.json` would drift out of sync with every edit.

## Decision

`scripts/generate-resume-pdf.cjs` follows the established build-script convention (ADR 0002): a plain CommonJS script, tested from `src/scripts/generateResumePdf/index.test.ts`, exporting `generateResumePdf(rootDir, logger)` and also runnable as a CLI. It reads `.aboutme/app-data.json` directly (ADR 0001) and renders two condensed PDFs with `pdfkit` — `public/Portfolio-DE.pdf` (German) and `public/Portfolio-EN.pdf` (English) — as a two-column CV, deliberately omitting the `projects` section. Named "Portfolio", not "Lebenslauf"/"Resume": this is the full, richly-detailed showcase document (skill-level bars, timeline, per-role tech pills); a separate, genuinely compact traditional CV is a distinct future document, not this one renamed. The sidebar color is derived from `app-data.json`'s `accentColor` (mixed 55% toward black) rather than hardcoded, so the PDF stays on-brand with the site. It reuses the `xxxDe`/`xxxEn` fallback convention from ADR 0003, reimplemented locally rather than importing `src/app-data/index.ts`, since that module resolves its language from `i18next` at runtime and isn't meaningful in a Node build-script context. The script is wired into `npm run web` and `npm run export:web` (after the data sync step so `.aboutme/` is current) and exposed standalone as `npm run generate:resume-pdf`. The app links to the generated files via a new `getResumePdfUrl(lang)` helper (`src/utils/resumePdfUrl`), which routes through `getVersionedLocalAssetUrl` per ADR 0006, from the contact footer (`WnaContactSection`) and from a standalone download button in the navigation drawer's footer (`WnaDrawerMenu`, alongside the theme toggle) — deliberately not a `WnaNavigationList` entry, since it's an action (open a file), not a route to navigate to, and an early version that mixed it into the route list rendered it as "active" whenever the drawer happened to show the home route as current.

The colored sidebar column runs down every page, not just page 1: on page 1 it shows the photo, name, title, a Kontakt block (each line with a small vector icon — see below), and a Tech-Stack skill-bar summary; on every page after that it shows a compact name label plus a Tools skill-bar section (`app-data.json`'s new `tools.primary`/`tools.secondary`, same shape as `techStack`, rendered with the same `buildSkillEntries`/`drawSkillBarSection` helpers). This replaced an earlier version that either repeated the _entire_ sidebar (photo, contact, tech-stack again) on every page, or dropped it to a thin header — both read as either duplicated content or an inconsistent, disappearing sidebar.

Contact rows in the sidebar draw a small icon next to each line via `drawVectorIcon`, which scales and fills an SVG path directly with pdfkit's `.path()`. The icon paths are imported from `@mdi/js` — the exact same constants `src/components/icon/WnaIcon/WnaIconMap.ts` uses for these icons in the app itself (plus Xing's hand-drawn path, copied from the same source, since Xing has no MDI icon) — so the PDF and the live site render identical glyphs from one source of truth.

Per-entry tech stack (inside each work experience block) renders as small pill badges (`drawPillRow`: rounded rects, wrapping left-to-right) rather than a `"·"`-joined text line, visually matching `WnaBadge`'s pill styling used elsewhere in the app. Phone numbers are grouped for readability (`formatPhoneNumber`) rather than shown as the raw unformatted digit string from `app-data.json`.

The avatar photo, if `profile.avatar` is set and the source file exists under `.aboutme/images/`, is always re-encoded through ImageMagick's `convert` (`-resize 240x240` to a temp PNG) rather than embedded as-is: pdfkit can only embed PNG/JPEG (the avatar is typically `.webp`), and an unresized source photo would otherwise bloat the PDF far beyond what a small sidebar circle needs (an early version embedded a full-resolution `.webp` avatar unmodified and produced a 2MB PDF; resizing brought it down to under 120KB). `convert` is already a conditional dependency of this repo's asset pipeline (`scripts/init-process.cjs`, `scripts/resizeImage.sh`), so this doesn't introduce a new external tool — if it's missing or the conversion fails, the script logs a warning and renders without a photo rather than failing the build.

## Consequences

- The resume PDFs are always in sync with `app-data.json` by construction — there's no separate document to remember to update.
- `pdfkit` resolves to a different build depending on the Node "exports" condition in play; under Jest's default RN test environment it resolves the ESM browser bundle instead of the Node CJS build and fails to parse, and Expo's globally-installed "winter" polyfills replace `TextDecoder`/`TextEncoder` with a stricter implementation that pdfkit's `fontkit` dependency doesn't expect. The test file works around both with a `@jest-environment node` docblock and by restoring Node's native `TextDecoder`/`TextEncoder` before requiring the script — noted here so the next Node-dependency-in-a-script case doesn't have to rediscover this.
- pdfkit's auto-flowing text cursor (`doc.x`/`doc.y`) and text style (`fillColor`/`font`/`fontSize`) are single shared, mutable document properties, not scoped to a drawing call. The explicit-position `.text(str, x, y, opts)` overload used to draw the sidebar leaves both the cursor and the style pointed at wherever/whatever the sidebar's last line used, rather than restoring either. This caused two bugs before it was understood: main-column content initially rendered starting from the sidebar's last cursor position (wrong x/y), and later, when work experience overflowed onto a second page, the paragraph interrupted by the page break resumed in the sidebar's pale text color instead of the body text color (because the page-break handler redraws the sidebar in between). Both are fixed by explicitly resetting `doc.x`/`doc.y` _and_ re-asserting `doc.font(...).fontSize(...).fillColor(TEXT_COLOR)` after every sidebar draw, not just once. `pdfkit`'s own `save()`/`restore()` does not help here — it only tracks the transformation matrix, not fill color or font.
- `doc.widthOfString(text, { fontSize })` silently ignores a `fontSize` passed via its options object — it only measures at whatever size was last set with `.fontSize()`. A first attempt at auto-shrinking the sidebar name to fit one line measured the same (wrong) width on every iteration and never actually shrank anything. `fitFontSize()` fixes this by calling `.fontSize(size)` before each `widthOfString` measurement.
- The sidebar is redrawn on every page pdfkit adds (via the `pageAdded` event) so the colored column runs continuously through the document instead of stopping after page 1.
- Bulleted detail lines use a manual hanging indent (bullet glyph drawn separately, then the detail text flowed from a shifted `doc.x`) rather than pdfkit's `indent` text option, which only indents a paragraph's first line — using it on a single `"•  " + text` string left wrapped continuation lines flush with the bullet instead of aligned under the text.
- Both `drawBulletPoint` and the per-entry pill row check the remaining space on the page and call `doc.addPage()` themselves before drawing if the content wouldn't fit, rather than letting pdfkit's automatic mid-text page break split a bullet's glyph from its (wrapped) text, or letting a pill row start right at the bottom margin and render partly off the page. `drawPillRow` tracks its own x/y cursor rather than pdfkit's auto-flow one, so it never triggers an automatic page break on its own — the check has to happen before calling it.
- Like `public/app-data.json` and `public/images/`, the generated PDFs are build artifacts, not source — they're `.gitignore`d and regenerated by CI/deploy, not committed. `app-data.json`'s new `tools` field, however, is source data (edited by hand like `techStack`), not a build artifact.

Later additions to this same design, kept here rather than as separate ADRs since they're incremental extensions of the same decision:

- **Proficiency levels**: `app-data.json` gained a flat `skillLevels` map (`{ "C#": "senior", ... }`, one of `junior`/`mid`/`senior`/`expert`, default `mid`) and a `softSkills.primary` list (`{ nameDe, nameEn, level }`). `techStack`/`tools` themselves stayed plain `string[]` — the live site's `WnaTechStackSection` reads `techStack` directly and expects strings, so `skillLevels` is a parallel lookup this script reads, rather than changing the shape of a field the app also depends on. Bar fill ratio is now driven by the looked-up level (`SKILL_LEVEL_RATIOS`), not by which array (primary/secondary) the item came from.
- **Experience timeline**: a dot-and-line timeline down the left edge of each Berufserfahrung entry, styled after the app's own `WnaExperienceSection`. Two page-break edge cases came out of this: (1) a bullet or pill row could get torn across a page break, splitting a bullet's glyph from its text — fixed by measuring each experience entry's _entire_ height up front and calling `doc.addPage()` before any of it is drawn if it won't fit as a whole; (2) the timeline line itself would just stop cold at a page boundary — fixed by capping the old page with a stub down to its bottom margin and leading into the next page's first dot from its top margin, using `doc.page = otherPageObject` directly (equivalent to what `switchToPage` does internally, but by object reference instead of buffered index) to draw on a page that isn't the current one.
- **Page footer** ("Seite X von Y"): requires `bufferPages: true` and a second pass after all content is drawn, using `doc.bufferedPageRange()` + `doc.switchToPage(i)`. This surfaced the same auto-page-break hazard as the timeline/bullet fixes from a different angle: drawing the footer at `page.height - 24` sits inside the real bottom margin on purpose, but pdfkit's overflow check doesn't care that the position was reached via `switchToPage` — it silently called `addPage()` on every iteration, re-firing the sidebar's `pageAdded` listener and doubling the page count. The general shape of this bug (a custom "how close to the bottom can I draw" threshold that doesn't match pdfkit's real `page.margins.bottom` check) also showed up inside the sidebar's own skill-bar list once it grew tall enough to reach it; the durable fix was to zero `page.margins.bottom` for the whole sidebar draw (and for the footer draw), rather than re-tuning whichever hardcoded threshold triggered it that time.
